# Method-grounding eval

An evaluation harness for the **Method section proposal**: does grounding a DESIGN.md in something specific (a physical object, a hard constraint, a governing metaphor) produce measurably better generations than tokens alone or adjective prose — holding everything else constant?

Generation runs through **Stitch** (`@google/stitch-sdk`); quantitative measurement is fully **deterministic** (no LLM judge); qualitative judgment happens in a **matrix viewer** with built-in blinding.

## Design cases

Each case under `cases/` is a rich, content-complete brief with a deep generic center, plus a ladder of arm documents whose front matter is byte-identical within the case (enforced at runtime) — only the prose grounding varies:

| case | deliverable | generic center it must escape | groundings (object / constraint / metaphor) |
|---|---|---|---|
| `agent-slides` | 7-slide technical talk on agent architecture (ReAct, Reflexion, worked NVDA trace, code, citations) | conference-deck template: dark theme, gradient title, icon bullets, agenda + thank-you slides | a 6.034/SICP-tradition lecture handout, photocopied that morning / every slide must survive the department photocopier / the deck embodies the closed feedback loop |
| `dc-tracks` | 6-panel prestige editorial home page cataloguing DC's running tracks (Georgetown, Anacostia, circuit map) | lifestyle-blog template: centered hero over darkened photo, rounded cards, icon stat badges | the 1923 athletics club's centenary annual crossed with a 1948 race programme / nothing may appear that doesn't physically exist at a track / the oval is a monument and the page is a lap of it |
| `auralis` | 7-section AI voice platform landing page (nav, demo panel, trust strip, dashboard, chat mockup) | the canonical AI-product page: dark mode, purple gradient hero, glowing icon cards | a Scandinavian lab-grade audio instrument / color may exist only where sound is rendered / the page is a recording studio and color is the voice behind the glass |

Per case, the arm ladder is: `no-design-md` (C0, defines the center) · `tokens-only` (C1) · `description` (C2, adjective prose — the baseline every treatment must beat) · `object` (T1) · `constraint` (T2) · `metaphor` (T3) · **`full-spec` (T-max)** — the complete designer-grade specification with enumerated Do's and Don'ts, per-element typography roles, and compositional rules. `full-spec` is the ceiling anchor: the gap between `object` (grounding only, zero stated don'ts) and `full-spec` (grounding plus every don't spelled out) directly measures how much of the prohibition work the grounding inherits for free — the sharpest form of H2. It is not length-matched; the others are.

**Prohibitions AND requirements.** Each `case.json` declares which basin features the intended design forbids and which it *requires* — `auralis` requires pill radii, the vivid gradient cloud, and icon glyphs on a light page, inverting the austerity of the other two cases. A violation is a prohibited feature present or a required feature missing. This keeps the harness grounding-relative rather than biased toward flat-print aesthetics.

**Injection channels.** Each DESIGN.md arm can run through two channels, because the channel is itself a model:

- `design-system` (default) — `upload_design_md` → `create_design_system_from_design_md` → generate with the asset attached. The product path, but Stitch's design-system extraction may flatten the prose treatment.
- `prompt` — the DESIGN.md embedded verbatim in the generation prompt. Bypasses the extraction pipeline.

If treatments beat `description` on the `prompt` channel but not the `design-system` channel, the pipeline is dropping the grounding before the generator sees it — a finding about Stitch, not the hypothesis. Prompt-channel cells appear as `<arm>+prompt`.

**Other controlled variables:** briefs carry all content (slide text, track names, section copy) and are identical across arms; prose length roughly matched between `description` and the T1–T3 treatments; no arm except `full-spec` contains a Do's and Don'ts section; same pinned model (`--model`, default `GEMINI_3_1_PRO`, recorded with the SDK version) per run; the control arm oversampled by default (2× `--samples`).

**Concurrency.** Cells run in parallel (`--concurrency`, default 3, max 8) — each cell is its own Stitch project, so concurrent generations can never confuse screen attribution. Samples *within* a cell stay serial deliberately: all of a cell's samples share one project, and the recovery path identifies a sample's screen by diffing new screens in that project — concurrent in-project generations would make that diff ambiguous. Workers get their own clients, a failed cell doesn't stop the others, and rate-limit-looking errors back off 30s.

**Eval snapshots.** Arm prose will be edited constantly — that's the workflow — so a run is only interpretable against the exact definition it saw. `generate.ts` copies every case definition into `runs/<id>/eval/` and stamps a per-case content hash plus a run-level `evalHash` into `config.json`. Resuming a run re-verifies the hashes and refuses if the definition (or model) has drifted — a run never mixes eval versions. `measure.ts` measures against the snapshot, not the working tree, and the viewer flags cases whose working-tree definition no longer matches the run (⚠ in the header strip). Two runs are comparable per case when their case hashes match.

## Hypotheses → metrics

| hypothesis (from the proposal) | metric | prediction |
|---|---|---|
| **H1 — grounding improves cross-generation consistency** | intra-arm dispersion: mean pairwise style-fingerprint distance within a cell | treatments < `description` < `tokens-only` < `no-design-md` |
| **H2 — negative constraints are inherited, not enumerated** | violation rates (prohibited present / required missing), stated nowhere except `full-spec` | `object` ≈ `full-spec` ≪ `description` — the grounding supplies what the don't-list would have |
| **H3 — grounding pulls output away from the generic center** | **excess distance from control**: mean fingerprint distance to `no-design-md` samples minus the control's own dispersion | treatments furthest from center |
| **H4 — prose drives adherence more than tokens** | occurrence-weighted palette adherence (OKLab ΔE to nearest token) and specified-font usage | prose arms ≥ tokens-only; if `tokens-only` ≈ prose arms, tokens do more work than the philosophy claims — also a useful result |

**Significance.** `measure.ts` runs two-sided permutation tests (10,000 resamples) for every treatment cell against its same-channel `description` baseline, per case, on three per-sample scalars: distance-from-control, violation count, and intra-arm dispersion. With small n, non-significance means underpowered, not "no effect".

## Running

```bash
cd evals/method-grounding
bun install

# Generate (each screen takes minutes; cells run in parallel — see --concurrency)
STITCH_API_KEY=... bun src/generate.ts --samples 5                                # all cases, design-system channel
STITCH_API_KEY=... bun src/generate.ts --cases auralis --channels design-system,prompt
# Pilot / resume (existing samples are skipped):
STITCH_API_KEY=... bun src/generate.ts --cases agent-slides --arms no-design-md,description,object --samples 2 --run pilot-1

# Measure (offline, instant, re-runnable)
bun src/measure.ts runs/<run-id>

# View the matrix
bun src/viewer.ts runs/<run-id>      # → http://localhost:4747

# No API key? Try the UI on synthetic caricatures:
bun src/demo.ts && bun src/measure.ts runs/demo && bun src/viewer.ts runs/demo
```

## The matrix viewer

`viewer.ts` is a **server-rendered Hono app** over the `runs/` root (`bun src/viewer.ts` → http://localhost:4747). Every view is a URL and all view state lives in query params, so any finding is a pasteable link; pages re-read the filesystem per request, so new samples and re-measures appear on reload. The only client JS is the compare tray and arrow-key navigation. Routing is Hono (`src/viewer.ts`); templates are typed server functions (`src/viewer/views.ts`) over a shared read layer (`src/viewer/data.ts`); a JSON API (`/api/runs`, `/api/run/<id>`) remains for scripting.

- **`/` — runs index.** Per run: model, eval-hash chip (chips sharing a color saw byte-identical definitions — directly comparable), per-case chips with sample counts, failure marks, and a headline (max excess distance, ✱ when significant vs description), measured/unmeasured status.
- **`/run/<id>?case=&channel=&size=&blind=&reveal=` — the matrix.** One column per cell in ladder order with metric badges (violations, excess distance, dispersion, palette adherence); every thumbnail carries its per-sample violation count and a **swatch strip of its dominant extracted colors** — palette drift is visible while scanning, before reading any number. Drift warning when the working tree no longer matches the run's snapshot. `blind=1` serves a deterministically shuffled, unlabeled grid with condition-revealing data hidden (swatch strips stay — they describe the output, not the condition); `reveal=1` restores labels.
- **`/run/<id>/cell/<case>/<cell>` — the cell inspector** (click any column header). The arm's DESIGN.md *as the run saw it* — rendered from the eval snapshot with token-reference highlighting and palette swatches, plus channel and provenance — beside its outputs, the per-sample metric table, the violation/requirement breakdown, and the permutation-test comparison vs `description`. The control cell explains itself in place of a document.
- **`/run/<id>/sample/<case>/<cell>/<i>` — the sample inspector**: the full rendered page beside its fingerprint — every check with its evidence count (forbid/require, ✗/✓), every extracted color with occurrence count and ΔE to its nearest palette token (flagged when off-palette), the font list with specified faces marked, and generation provenance (model, channel, elapsed, design-system asset, links to the raw HTML/screenshot/metadata and the cell's raw MCP responses). ←/→ traversal, pin-to-compare. While blinded, provenance and raw links are hidden; the fingerprint stays, since it describes only the output. Fingerprints are computed on demand from the HTML (mtime-cached), so this works on unmeasured runs too.
- **`/compare?items=run/case/cell/i,…` — side-by-side panes.** Items are fully qualified with their run, so **cross-run comparison** (model A vs B, before/after a prose edit) works directly; labels carry the run when panes differ.
- **Judgment capture.** Every sample page has a verdict form (good / mixed / poor + note) persisting to `runs/<id>/judgments.json` with a `blinded` flag recording whether the verdict was given blind — the credible kind. While blinded, submitting auto-advances to the next shuffled sample, so a blind sweep is look → verdict → next. Verdicts surface as a `human n✓` badge on matrix column headers, a per-sample column in the cell inspector (with `(blind)` markers), and a judged count on the runs index. These are the calibration target for any future LLM judge.
- **Generation from the viewer.** `+ new run` on the index opens `/new-run`: cases load dynamically from `cases/` (with their current definition hashes), plus arm/channel checkboxes, sample counts, model, and run name. Submitting spawns `generate.ts` as a subprocess (one job at a time), streams output to `runs/<id>/generate.log`, auto-measures on completion, and shows a live banner with log tail and cancel on the run page (auto-refreshing while running). Failed or partial runs get **resume / extend generation** (replays the stored config through the snapshot and model guards; existing samples are kept) and unmeasured runs get **measure now**.
- **Case authoring (`/cases`).** The case library shows every case (and draft) with its definition hash, validation status, and which runs used it at which hash. `/cases/new` scaffolds a draft at `cases/<key>.draft/` — invisible to runs until promoted — from a brief, flags, and either bare YAML tokens or a **pasted custom DESIGN.md** (front matter → shared tokens, prose → the `full-spec` arm). The case detail page renders every arm with the same doc renderer as the cell inspector and runs the **mechanical validation gate** per reload: front-matter byte-identity, per-arm lint via the repo CLI (content-hash cached), TODO placeholders, Do's-and-Don'ts placement (only `full-spec` may have one), length parity (C2 vs T1–T3 within ±35%), known prohibition/requirement flags, and brief completeness. Editing happens in your editor; the page revalidates on reload; **promote** (gated on zero errors) renames the draft into `cases/` where the new-run form picks it up immediately.
- **Ideation → commit → projection (the primary creation flow).** The generative taxonomy: spark → brief → direction → {tokens, groundings, flags} → arms → runs — leverage equals height, the arms are five *projections* of one direction (a prism, not five documents), and the tree gives precise invalidation semantics. `/cases/new` starts with a **spark**; an **ideation-mode session** (`authoring/ideate.md`; tools limited to `read_concept`/`capture_brief`/`capture_direction` — system knowledge without production access, the fix for the blank page that doesn't take the page away) diverges on worlds, names the generic center as the shared enemy, converges with the human, and captures only on agreement. The concept (`concepts/<id>/`) holds the spark plus the two captures; **commit** (a human act, gated on both) scaffolds the draft from the direction document (front matter → tokens, prose → full-spec) and fires a **projection turn** (`authoring/project.md`): refract the committed world into description/object/constraint/metaphor, validate until clean. Live-proven end to end: the gate caught ideation's loose token YAML and the production agent normalized it via `write_tokens` before passing — the modes police each other through the mechanical gate.
- **Wholesale generation (the expert path).** `/cases/new` is two fields: a **key and a brief** (plus optional tokens or a custom DESIGN.md). "Create & hand to agent" scaffolds the draft and immediately fires a kickoff turn (`authoring/kickoff.md`, versioned) — the agent tightens the brief if thin, designs the token system, writes title/genericCenter/flags/device into case.json, picks groundings for all three method slots, drafts all five arms, and loops `validate_case` until clean — while you land on the case page watching it stream in the editor, every change reviewable as per-file diffs. "Create empty draft" preserves the manual path. The brief remains the human's irreducible input; everything downstream is steerable conversation.
- **Agentic authoring (Phase B).** Draft case pages carry an agent panel running `claude -p` through the jobs system: **propose groundings** returns 2–3 edged candidates per method slot with rationale and an honest risk (`.authoring/proposals.md`, rendered inline); **draft arms** writes the selected arms from the brief + grounding seeds (blank seeds → the agent invents), using one hand-built case as the canonical few-shot and the invariants as explicit rules. The agent never touches disk — it emits `===FILE…===` blocks, and the harness writes them with the **canonical front matter re-attached**, so token identity holds by construction; output then flows through the same validation gate and human review as hand-written arms. Configuration: `authoring/claude-settings.json` is Claude Code's **native settings format** (model, fallbackModel, effortLevel, …) passed via `--settings`; prompts are versioned at `authoring/propose.md` / `authoring/draft.md`. Harness-fixed flags: `--tools ""` (no tool use), `--output-format json` (cost logged per job), prompt via stdin, and **`ANTHROPIC_API_KEY` stripped from the child env** — in `-p` mode a present key is always used, silently switching billing from the subscription to the API. Remaining: Phase C (basin probing feeds `genericCenter`/prohibitions from measured control samples) and Phase D (the edit→revalidate→rerun loop).
- **In-UI editing runtime (in progress).** The interactive authoring loop is built on `@inbrowser/agent` (agent runtime: sessions, ReAct strategy, tool registry, event stream) + `@inbrowser/relay` (provider plug-ins — Anthropic, Gemini, OpenRouter, **Ollama for local models** — and a resumable SSE transport), vendored as tarballs in `vendor/` with `@inbrowser/resumable` wired via a package.json override. The seam is `src/agent/llm-bridge.ts` (`relayProviderAsLlmClient`): relay `InferenceProvider` → agent `LlmClient`, proven by `test/bridge.test.ts` (deterministic scripted provider driving a full session tool round-trip) and `test/bridge-live.test.ts` (auto-skipping live smoke against local Ollama). Topology: the agent session runs server-side in the Hono process where tools touch `cases/<key>.draft/`; the browser renders the session event stream — the case editor becomes the viewer's one interactive island while everything else stays SSR. `claude -p` jobs remain for subscription-billed batch drafting.

  The island is live: every draft case page carries an **interactive editor** — a chat panel that bootstraps from `/edit/transcript`, posts turns, and renders the SSE stream as it happens (streaming text, tool chips resolving from ⏳ to their summaries). Each completed turn shows **per-file diffs** of what it actually changed on disk (snapshot-before vs snapshot-after, unified hunks, +/− colored) — required, not decorative, because a turn may touch files beyond the literal ask (parity rebalancing, token sync) and drafts have no git safety net. EventSource reconnects resume via `Last-Event-ID`, so a refreshed tab rejoins an in-flight turn mid-stream. Enter sends; reset drops session history without touching files.

  The server side: `src/agent/tools.ts` binds eight tools to a draft (`read_brief`, `read_tokens`, `write_tokens` — which synchronizes front matter across **all** arms, `read_arm`, `write_arm` — canonical front matter re-attached on every write, `validate_case` — **the gate as a tool**, so the loop is draft → validate → fix inside one session, `update_case_json`, `read_proposals`). `src/agent/sessions.ts` holds one session per draft case (independent of the generation-job slot), with turns running as jobs on an in-memory resumable engine. Routes: `POST /cases/:key/edit/messages` → `{jobId}`; `GET /cases/:key/edit/stream?job=&from=` → SSE with seq ids (a refreshed tab replays from any offset; terminal jobs replay fully); `GET /cases/:key/edit/transcript`; `POST /cases/:key/edit/reset`. Provider selection lives in `.agent-provider.json` (gitignored; default local Ollama) — free local iteration, frontier provider for the final pass. The Stitch API key can be pasted in the UI instead of restarting the viewer with `STITCH_API_KEY` set. Stored in `.stitch-key` inside the eval package (gitignored, mode 0600, shown only masked), injected into job environments, and taking precedence over the environment variable. **save & verify** makes one `list_projects` call so a bad key is caught before a run is spent on it. The new-run form's key badge links here and names the active source.

`blind.ts` remains for a file-based blind workflow.

## How measurement works

`src/fingerprint.ts` extracts a deterministic style fingerprint from each generated HTML document — explicit colors (hex/rgb/hsl, converted to OKLab and occurrence-weighted), gradient/shadow/rounded/bold usage and icon-font usage (CSS declarations *and* Tailwind utility classes), font families (declarations + Google Fonts requests, icon fonts excluded), and background lightness. Distances between fingerprints combine Jaccard distance over quantized color sets and font sets with normalized differences of the numeric features.

## Reading the results

- **Thesis confirmed:** excess distance rises along the ladder in every case, treatments beat `description` with p < 0.05, and `object` lands near `full-spec` on violations without a single stated don't.
- **Complicated but interesting:** treatments beat `description` on distance but lose on dispersion or palette adherence — grounding buys distinctiveness at the cost of predictability or fidelity. Or `full-spec` ≫ `object` on violations — prohibitions are NOT inherited and the don't-list earns its keep.
- **Thesis threatened:** `description` sits as far from center as the treatments — a well-formed document helps regardless of grounding. The controls are deliberately strong so the experiment *can* return this answer.
- **Channel artifact:** treatments win on `+prompt` cells but not design-system cells — Stitch's extraction pipeline is flattening prose; fix the pipeline before re-testing the hypothesis.
- **Case-dependent:** effects appear in `auralis` (deepest basin) but not `dc-tracks` — grounding strength may matter most where the gravity well is deepest.

## Known limitations

- **Lexical, not rendered.** Counting `shadow-md` in markup is not the same as measuring rendered pixels; named Tailwind palette classes other than white/black are not resolved. A headless-browser pass (computed styles + screenshot pHash) is the natural v2 — and the hand-drawn-diagram register of `agent-slides` is only judgeable visually, in the viewer.
- **Occurrence counts ≠ visual area.** A color used once on a 90%-area background weighs the same as a one-off icon tint.
- **Small N.** 5 samples per cell shows direction, not significance — the permutation tests will say so honestly.
- **Prompt-channel verbosity confound.** Channel comparisons are valid within a channel; cross-channel gaps diagnose the pipeline, not the hypothesis. `full-spec` is likewise not length-matched — it answers "what does the ceiling look like", not "what does grounding alone buy".
- **Vendored SDK.** `@google/stitch-sdk` resolves to `vendor/google-stitch-sdk-0.3.5-local.tgz`, built from the local `~/repos/davideast/stitch-sdk` checkout (commit `4e1a5ba`: generation results return ALL screens — fixes truncated screen lists that broke polling recovery). Rebuild with `cd packages/sdk && bun run build && npm pack`, then replace the tarball and `bun install`. Switch back to the registry version once the fix is published.
- **Screen recovery is response-shape-tolerant.** `stitch.ts` extracts screen-shaped objects from anywhere in a response (`htmlCode.downloadUrl` nests below the discriminating key), accepts only DESIGN-typed screens (Stitch projects also contain IMAGE screens — generated photography that can carry `htmlCode` — and `asset-stub-*` design-system entries), and polls `list_screens`/`get_screen` whenever a renderable screen is missing, not only when the call throws. Validated by replaying the extraction against real failed-run responses in `runs/*/raw/`.
- **Tokens are held fixed.** Letting each method produce its own token set (the ecologically real case) is a planned phase two.
